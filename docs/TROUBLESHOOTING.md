## 1. pip install 시 UnicodeDecodeError (cp949)

**증상**
```
ERROR: Exception:
UnicodeDecodeError: 'cp949' codec can't decode byte 0xec in position 2:
illegal multibyte sequence
```

**원인**
`requirements.txt`에 한글 주석이 들어 있었다. pip은 이 파일을 **시스템 로케일
인코딩(한국어 Windows = cp949)** 으로 읽는데, 파일은 UTF-8로 저장돼 있어
첫 한글 글자의 바이트에서 디코딩이 실패했다.

`position 2` = 3번째 바이트 = `# ` 다음의 첫 한글 문자.

**해결**
`requirements.txt`를 ASCII 전용으로 변경.

**일반화**
- 파이썬 소스(`.py`)는 UTF-8이 기본이라 한글 주석이 안전하다.
- 그러나 **외부 도구가 읽는 설정 파일**(requirements.txt 등)은 그 도구의 규칙을 따른다.
- 그래서 이 프로젝트의 파일 읽기 코드에는 전부 `encoding="utf-8"`을 명시해 두었다.
  명시하지 않으면 같은 코드가 Windows와 Mac에서 다르게 동작한다.

## 2. PowerShell 리다이렉트가 UTF-16으로 저장됨

**증상 (잠재적)**
`pip freeze > requirements.lock.txt` 로 만든 파일을 나중에 읽을 때 인코딩 오류.

**원인**
Windows PowerShell의 `>` 는 기본적으로 UTF-16으로 파일을 쓴다.

**해결**
```powershell
pip freeze | Out-File -Encoding utf8 requirements.lock.txt
```

## 3. OpenAI 429 — insufficient_quota

**증상**
```
openai.RateLimitError: Error code: 429
'You have no credits remaining.'  code: 'credit_balance_exhausted'
```

**원인**
API 키는 유효하지만 계정 크레딧 잔액이 0. OpenAI는 신규 계정에 무료 크레딧을 주지
않으므로, 결제 수단을 등록해도 **크레딧을 따로 충전**해야 한다.

**구분 포인트**
- `AuthenticationError` → 키 자체가 잘못됨
- `RateLimitError` + `insufficient_quota` → 키는 정상, 잔액 문제
- `RateLimitError` + `rate_limit_exceeded` → 호출이 너무 잦음 (잠시 후 재시도)

**해결**
platform.openai.com → Billing → Add credits.

## 4. 답이 문서에 있는데도 에이전트가 "모른다"고 거절함 (과잉 거절)

**증상**
평가 1차에서 rag 카테고리 8문항 중 1개 실패(#5). 도구를 **아예 부르지 않고** 거절했다.

```
질문: TensorRT FP16 변환 효과가 1.15배에 그친 이유가 뭔가요?
used_tools: []
답변: "해당 정보는 문서에 명시되어 있지 않기 때문에 답변을 드릴 수 없습니다."
```

그런데 답은 `data/docs/04_deployment_spec.md:16` 에 그대로 적혀 있었다.
("병목이 GPU가 아니라 CPU였기 때문에 GPU 연산을 빠르게 해도 전체 시간은 거의 줄지 않았다")

**1차 시도 — 시스템 프롬프트 수정 (실패)**
거절 규칙이 검색 규칙보다 먼저 적용된 것이라 보고, `src/agent.py` 의 SYSTEM_PROMPT 에서
검색 규칙을 맨 위로 올리고 거절 대상을 3가지로 열거했다.
→ **결과 변화 없음. 여전히 검색 없이 거절.** rag 88% 유지.

**원인**
LLM이 도구를 부를지 말지 고르는 근거는 시스템 프롬프트가 아니라 **도구의 docstring**이다.
`search_inspection_docs` 의 설명은 "검사 기준, 실험 이력, 라벨 이슈, 배포 사양 등"
이었는데, LLM 입장에서 `TensorRT FP16` 은 일반적인 추론 최적화 기술로 읽히므로
"이 시스템 문서의 범위 밖"이라고 분류해 버렸다.

즉 **문제는 태도(프롬프트)가 아니라 명세(도구 설명)** 였다.

**해결**
docstring에 코퍼스의 실제 주제를 열거했다. 문서 제목이 아니라 **질문자가 쓸 단어**로 적었다.

```python
- 배포 사양: 처리 시간 실측, CPU/GPU 병목 분석, **TensorRT FP16 등 최적화 시도**,
  인스턴스 선정, 운영점(conf threshold) 결정 근거, 파이프라인 5단계
```

→ **rag 88% → 100%, 전체 95% → 100%.**

**일반화 — 면접에서 쓸 문장**
도구 선택이 틀렸을 때 고쳐야 할 곳은 세 군데이고, 순서가 있다.

1. **도구 설명(docstring)** ← LLM이 선택에 쓰는 1차 근거. 여기를 먼저 본다.
2. **도구 경계** — 한 도구가 두 가지 일을 하고 있지 않은가.
3. **시스템 프롬프트** — 태도와 말투. 선택 문제를 여기서 고치려 하면 위 사례처럼 실패한다.

이 순서를 몰라서 프롬프트만 계속 고치는 것이 흔한 시간 낭비다.

**부수 확인**
거절 대상을 좁혔으므로 `refuse` 3문항이 깨질 위험이 있었으나, 재측정 결과 100% 유지였다.
**위험을 예상했고 측정으로 확인했다** — 평가셋이 있어서 가능한 확인이다.

## 5. 검색은 제대로 됐는데 평가에서 실패로 나옴 (평가셋 정답 라벨 오류)

**증상**
T8 파라미터 비교에서 rag 2번 문항(`"tiled 모델을 배포하지 않기로 한 근거"`)이
**두 설정 모두 실패**로 나왔다.

**하려던 잘못된 해석**
"임베딩이 질문의 `tiled` 와 문서의 `SAHI` 사이 어휘 간극을 못 메운다.
하이브리드 검색(BM25 + 벡터)이나 query rewriting 이 필요하다."

**실제 원인**
검증용 정답 문자열을 `오탐` 으로 잡아둔 것이 틀렸다.

- `오탐`(각인·이음매) 은 **타일 경계 처리** 이야기다 (`02_experiment_log.md:21`)
- tiled 모델을 배포하지 **않은** 근거는 **홀드아웃에서 붕괴** 다 (`:13`, `:16`)

검색은 정확히 맞는 청크를 가져오고 있었다. **채점 기준이 틀렸던 것이다.**

**해결**
`eval/retrieval_check.py` 의 정답 문자열을 `붕괴` 로 수정.
→ 설정 A의 검색 정확도 88% → **100%**.

**일반화 — 이 프로젝트에서 가장 중요한 기록**
평가셋의 정답 라벨이 틀리면, 시스템이 맞았는데도 틀렸다고 나온다.
그 상태에서 원인을 시스템에서 찾기 시작하면 **존재하지 않는 문제를 고치느라
시간을 쓴다.** 하이브리드 검색을 붙였다면 반나절을 썼을 것이고, 숫자는
"고쳐졌다"고 나왔을 것이다(원래 맞았으니까). 잘못된 성공 서사가 하나 생겼을 것이다.

원 프로젝트에서 라벨이 틀린 셀 9개 때문에 F1이 0.147 낮게 나왔던 일(해당 이미지를 학습에서 빼고 재학습하자 회복)과 같은 구조다.
**모델을 의심하기 전에 정답을 의심한다.** 같은 교훈을 평가셋에서 다시 만났다.

점검 순서:
1. 정답 라벨이 맞는가 ← 가장 싸고, 가장 자주 원인이다
2. 측정 코드가 맞는가
3. 그다음에 시스템을 의심한다

## 6. 계산 결과에 문서 출처를 갖다 붙임 (출처 오귀속)

**증상**
복합 질문에서 `simulate_threshold` 가 **계산한** 수치에 문서 출처가 붙었다.

```
"임계값을 0.3으로 올리면 recall은 0.628... (출처: 02_experiment_log.md)"
                                            ↑ 문서에 없는 값이다. 방금 코드가 계산했다.
```

내용은 맞지만 **근거의 출처가 거짓**이다. 이 답변을 받은 담당자가 해당 문서를 열면
그 숫자는 없다. 검증하려는 사람을 엉뚱한 곳으로 보낸다.

**1차 시도 — 시스템 프롬프트 (실패)**
```
- 출처는 문서 검색 결과에만 붙이세요. 도구가 계산한 수치는 출처를 붙이지 마세요.
```
→ **전혀 고쳐지지 않았다.** 여전히 계산 결과에 출처를 붙였다.

**원인**
LLM은 컨텍스트에 **실제로 있는 것**에 훨씬 강하게 반응한다.
`ToolMessage` 로 들어온 검색 결과에는 `[출처: ...]` 문자열이 눈앞에 있고,
"붙이지 말라"는 프롬프트 규칙은 멀리 떨어진 추상적 지시다.
바로 앞에 보이는 패턴이 이긴다.

**해결 — 규칙을 지시가 아니라 데이터로 준다**
도구가 돌려주는 문자열의 **첫 줄**에 표시를 넣었다 (`src/tools.py` 의 `_NO_SOURCE_NOTE`).

```
[계산 결과 — 표에서 직접 계산한 값이므로 문서 출처가 없습니다. 출처를 붙이지 마세요.]
임계값 0.3 적용 결과
- Recall: 0.628 ...
```

→ 복합 질문 3개 재확인 결과, 문서 근거 문단에만 출처가 붙고 계산 문단에는 붙지 않았다.
도구 선택 정확도 100% 유지(회귀 없음).

**일반화 — 이 프로젝트에서 두 번 나온 패턴**
| 문제 | 프롬프트로 고치기 | 실제로 통한 것 |
|---|---|---|
| 과잉 거절 (4번) | 실패 | 도구 **docstring** 수정 |
| 출처 오귀속 (6번) | 실패 | 도구 **반환값**에 표시 삽입 |

**LLM의 행동을 바꾸려면 프롬프트보다 컨텍스트를 바꾸는 편이 안정적이다.**
프롬프트는 태도를 정하고, 도구의 명세와 출력은 행동을 정한다.
프롬프트만 고치며 시간을 쓰는 것이 이 분야에서 가장 흔한 낭비다.

## 7. 유도 질문에 동조하며 근거를 지어냄 — 평가셋이 못 잡은 실패

**발견 경위**
평가가 아니라 **실사용 중**에 나왔다. 문서 내용을 확인하려고 CLI로 질문하다가 발견했다.

```
질문: 0.651→0.798는 재학습이 아니라 평가 데이터 정제인가?
답변: ...평가 데이터 정제와 관련이 있습니다. 이 변화는 평가 프로토콜에서
      동분포와 홀드아웃 평가의 차이를 반영하며, 특히 홀드아웃 평가에서
      성능이 향상된 것으로 보입니다. [출처: 01_evaluation_protocol.md]
```

**무엇이 틀렸나 — 세 가지**

| # | 문제 | 실제 |
|---|---|---|
| 1 | 출처 오귀속 | `0.651/0.798` 는 `03_mislabel_issue.md:16` 에만 있다. 인용된 `01` 에는 **그 수치가 없다** |
| 2 | 근거 환각 | "동분포/홀드아웃 차이" 는 문서에 없는 설명. 실제 원인은 **라벨 오류 셀 9개의 이미지를 학습에서 빼고 재학습**한 것(평가셋은 그대로 — 7-e 참조) |
| 3 | 추측 표현 | "~것으로 보입니다" — 문서 근거 답변에 추측이 섞였다 |

**왜 이렇게 됐나**
질문이 전제를 담은 **유도 질문**이었다("A가 아니라 B인가?"). 앞부분은 당시 03 문서와
일치했지만 그건 **질문이 문서와 같은 말을 했기 때문**이지 시스템이 확인한 것이 아니다.
(그 03 서술 자체도 원자료와 달라 나중에 정정했다 — 7-e.) 그리고 남은 설명을
채우면서, 검색된 다른 청크(`01` 의 동분포/홀드아웃 절, `03` 의 교훈 절에도
동분포·홀드아웃 언급이 있다)에서 내용을 끌어왔다.

**왜 평가셋 20문항이 못 잡았나** ★ 이게 핵심이다
1. 20문항이 **전부 중립적으로** 쓰여 있었다. 거짓 전제를 들이미는 질문이 없었다.
2. 자동 채점이 **'도구를 골랐는가'까지만** 이었다. 이 답변은 올바른 도구
   (`search_inspection_docs`)를 정확히 불렀으므로 **도구 선택 100% 안에 포함된다.**
   출처가 맞는지는 사람이 CSV를 열어 봐야만 알 수 있었다.

즉 **지표가 통과했는데 시스템은 틀렸다.** 평가셋이 있다고 안심하면 안 된다는 사례다.

**조치 — 평가셋 보강 (2026-09-28)**

| 추가한 것 | 내용 |
|---|---|
| `leading` 카테고리 5문항 | 거짓 전제를 담은 유도 질문 (21~25번) |
| `expected_source` 자동 채점 | 답변이 **올바른 파일명**을 인용했는지 기계가 확인 |
| `must_contain` 자동 채점 | 정답 대목에만 나오는 **사실 앵커**가 답변에 있는지 확인 |

사실 앵커 예: 24번("FP16으로 3배 빨라진 거 맞죠?")의 앵커는 `"1.1"`.
거짓 전제에 동의하면 이 문자열이 나올 수 없으므로 **끌려갔는지가 드러난다.**

**일반화**
- **평가셋은 한 번 만들고 끝나지 않는다.** 실사용에서 나온 실패 유형을 계속 흡수해야 한다.
- **중립적인 질문만으로 테스트하면 유도에 약한 것을 못 본다.** 사용자는 중립적으로 묻지 않는다.
- 자동 채점 항목이 적으면 **"지표는 통과했는데 틀린"** 구간이 생긴다.
  이 프로젝트에서는 그 구간이 '출처'였다.

**사용 시 주의 (README 한계 절에도 기재)**
- 열어놓고 묻는다: ✅ `"F1이 0.651에서 0.798로 오른 이유가 뭐야?"`
- 정답을 담아 묻지 않는다: ❌ `"재학습이 아니라 평가 데이터 정제인가?"`
- **출처 파일명을 반드시 열어 확인한다.** 이번 건은 파일만 열어봤어도 5초에 잡혔다.

**보강 후 결과 (2026-09-28)**
25문항 전부 도구·출처·사실 100%. `leading` 5문항 모두 거짓 전제를 명시적으로 부정했다.
다만 아래 세 가지가 함께 드러났다. **숫자보다 이쪽이 중요하다.**

### 7-a. 내가 만든 채점 기준이 또 틀렸다 (측정기 버그 2회차)

22번("CT/EXT를 합쳐서 학습한 거 맞나요?")의 사실 앵커를 `"분리"` 하나로 잡았다.
시스템은 이렇게 답했다.

> "하나의 멀티모달 모델로 **묶지 않고** 두 개의 **독립** 파이프라인으로 설계되었습니다"

**완벽히 맞는 답인데 실패로 찍혔다.** 같은 뜻을 다른 낱말로 썼을 뿐이다.
5번 항목(T8 정답 라벨 오류)과 **똑같은 실수의 재발**이다.

→ 이번에는 키워드만 바꾸지 않고 **측정기를 고쳤다.** 표현이 갈릴 수 있는 앵커는
`must_contain_any`(OR) 로 받게 해서, 채점이 문체에 흔들리지 않게 했다.

**교훈**: 같은 실수가 두 번 나오면 그 사례를 고칠 게 아니라 **도구를 고쳐야 한다.**

### 7-b. 출처 채점이 느슨해서 과대 통과했다

21번 답변이 `01` 과 `03` 을 나란히 인용했다. `0.651/0.798` 는 `03` 에만 있으므로
`01` 은 불필요한 인용이다. 그런데 채점이 `expected in answer` 였던 탓에
**맞는 출처가 하나라도 있으면 통과**시켰다.

→ 기대 출처가 있어야 하고 **다른 코퍼스 문서가 섞이면 실패**로 바꿨다.
또 `cited_sources` 컬럼을 추가했다. CSV 의 `answer` 가 400자에서 잘려
2번 문항은 출처가 아예 보이지 않았는데, **사람이 눈으로 검증할 수 없으면
수동 채점 칸이 무의미하다.**

### 7-c. 같은 질문인데 실행마다 답이 달랐다 ★

| 실행 | 21번이 인용한 출처 |
|---|---|
| 1차 | `01_evaluation_protocol.md`, `03_mislabel_issue.md` ← 01 은 오귀속 |
| 2차 | `03_mislabel_issue.md` ← 정확 |

`temperature=0` 인데도 갈렸다. 즉 **2차의 `출처 100%` 는 고쳐져서가 아니라
이번 판에 안 나온 것**일 수 있다. 1회 측정으로 "고쳤다"고 말하면 안 된다.

→ EXPERIMENTS.md 의 한계 4번("각 설정을 1회만 측정했다")이 **추정이 아니라
실제로 관측됐다.** 엄밀하게는 3회 반복 후 최악값을 보고해야 한다.

### 7-d. 자동 지표를 전부 통과하고도 내용이 틀린 경우

수동 채점에서 3번·7번이 걸렸다. 둘 다 **도구·출처·사실 앵커 세 지표를 모두 통과**했다.

- **3번**: CT/EXT 분리 이유로 "SAHI 오탐"을 들었다 — 타일 경계 처리 이야기이고 분리와 무관
- **7번**: EXT 점 recall 의 한계로 "타일 경계 오탐"을 들었다 — CT/SAHI 이슈

사실 자체는 문서에 있지만 **연결이 날조**다. 검색된 청크 여러 개의 내용을 섞은 결과다.
문자열 검사로는 원리적으로 잡히지 않는다.

**결론**: 자동 채점은 형식을 보고, 사람은 내용을 본다. 자동화 비율을 높이는 것과
**자동화로 덮이지 않는 구간을 아는 것**은 다른 일이다.

### 7-e. 코퍼스 자체가 원자료와 달랐다 (2026-09-29 정정)

원 프로젝트의 작업 로그와 대조하다가 코퍼스 두 곳이
다르게 적혀 있는 것을 찾았다. 에이전트는 코퍼스대로 답했으므로 채점은 통과했지만,
**채점 기준이 된 문서가 틀리면 "정확한 답"도 틀린 답이 된다.**

| 문서 | 코퍼스에 적혀 있던 것 | 원자료 |
|---|---|---|
| `03_mislabel_issue.md` | 모델은 수정하지 않고 9개 셀을 **평가에서 제외** | 오라벨 이미지를 **학습에서 제외하고 재학습**. 평가는 같은 홀드아웃 380장이고, 그 7개 셀에는 오라벨 셀이 없음 |
| `02_experiment_log.md` | 챔피언의 동분포/홀드아웃 F1 을 **같은 모델의 두 측정**으로 적어 둠 | 두 값은 **서로 다른 모델 · 평가셋**이었다. 전 셀을 학습한 챔피언은 홀드아웃을 잴 수 없고, 일반화는 분할만 바꾼 별도 모델로 따로 쟀다 |

**평가셋도 함께 바뀌었다.**
- 21번: 기존 질문("재학습해서 맞죠?")의 전제가 사실이었다. 거짓 전제인 "평가 데이터에서 뺐죠?"로 바꾸고, 앵커를 "재학습"으로 바꿨다.
- 23번: 앵커를 챔피언 모델명과 tiled 홀드아웃 F1 중 하나로 받도록 바꿨다.
- 4번: 질문 문구 "평가에서 제외"를 "학습에서 제외"로 바꿨다.
