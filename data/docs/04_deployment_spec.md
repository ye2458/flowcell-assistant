# 배포 사양 및 운영점 결정

> 공개용 합성 기록입니다. 인스턴스·처리 시간·수치는 실제 값이 아닙니다.
> 단, 운영점 수치는 `data/inspection_results.csv` 와 일치하도록 맞춰져 있습니다.

## 처리 시간 실측

기준 장비에서 셀 1개 처리에 **4.2분**이 걸린다.

병목을 프로파일링한 결과 **CPU 61% / GPU 39%** 로 CPU가 병목이었다.
GPU 연산이 병목일 것이라는 처음의 가정과 반대였다.
원인은 SAHI 타일 분할과 결과 병합이 CPU에서 수행되기 때문이다.

주의: 이 비율은 기준 장비 기준이다. 더 낮은 등급의 GPU에서는 GPU 71%로 역전되므로
"CPU가 병목이다"라는 결론은 장비에 종속적이다.

## 최적화 시도

TensorRT FP16 변환을 적용했으나 **1.15배** 개선에 그쳤다.
병목이 GPU가 아니라 CPU였기 때문에, GPU 연산을 빠르게 해도 전체 시간은
거의 줄지 않았다. 최적화는 병목을 먼저 찾은 뒤에 해야 한다.

## 최종 배포 구성

- 인스턴스: **g4dn.2xlarge 이상**
- 처리 방식: **SQS 기반 비동기 큐**

동기 처리로는 요청이 몰릴 때 4.2분 대기가 그대로 쌓인다.
검사는 실시간 응답이 필수가 아니므로 비동기 큐가 적합하다고 판단했다.

## 운영점(conf threshold) 결정

채택값: **conf = 0.05**

| 항목 | 값 |
|---|---|
| Recall | 0.977 |
| 재검 부하 | 6.6% |

F1이 최대가 되는 지점은 conf 0.12 였으나 채택하지 않았다.

이유: 불량이 유출되면 회수와 신뢰 손실 비용이 발생하는 반면,
재검은 사람이 다시 보는 비용에 그친다. 두 비용이 대칭이 아니므로
재검 부하 6.6%를 감수하고 recall 0.977을 택했다.

**운영점은 성능 지표가 아니라 운용 부하와 비용 구조가 결정한다.**
