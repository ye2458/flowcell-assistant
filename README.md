# CELLNEX Inspection Assistant

이차전지 셀 검사 담당자가 묻는 세 종류의 질문을 하나의 에이전트가 처리하는 운영 어시스턴트.
RAG와 Tool-calling Agent를 LangGraph로 묶었다.

| 질문 | 처리 방식 | 도구 |
|---|---|---|
| 왜 그렇게 판단했나 | 문서에서 근거를 찾아 출처와 함께 답한다 | `search_inspection_docs` |
| 몇 건인가 | 검사 결과 표를 센다 | `query_defect_stats` |
| 임계값을 바꾸면 어떻게 되나 | recall과 재검 부하를 다시 계산한다 | `simulate_threshold` |

세는 일과 계산하는 일은 코드가 하고, LLM은 어떤 도구를 부를지만 고른다.

> **데이터 안내.** `data/docs/`는 공개용으로 만든 합성 기록이다.
> 원래는 작성자가 비전 검출 팀 프로젝트에서 직접 쓴 문서로 개발했으나 팀 산출물이라
> 공개하지 않는다. 공개본은 문서 구조와 판단 논리를 그대로 두고 모델명·수치·셀 ID만 바꿨다.
> 검사 결과 표도 처음부터 합성 데이터다. 이 저장소의 수치는 실제 모델 성능이 아니다.

## 왜 도구를 세 개로 나눴나

`"confidence 0.3 이하인 REJECT 셀이 몇 개인가?"`를 벡터 검색으로 풀면 반드시 틀린다.
벡터 검색은 의미가 비슷한 문장을 찾을 뿐, 1,000행을 세지 못한다.

세는 일은 언제 돌려도 같은 답이 나와야 하므로 코드가 맡았다.
LLM에게 남긴 역할은 "어떤 도구를 부를지 고르는 판단" 하나다.
RAG 챗봇과 Agent의 차이가 여기에 있다.

`simulate_threshold`를 따로 둔 이유는 조금 다르다.
문서만 검색하는 어시스턴트는 "문서에 뭐라고 쓰여 있는지"를 되풀이한다.
이 도구는 임계값을 바꿨을 때의 수치를 직접 계산하므로, 운영 판단 자체를 바꾼다.
*F1 최대점은 배포 운영점이 아니다* 라는 원칙을 실행 가능한 형태로 옮긴 것이다.

## 실행

```bash
# 가상환경
python -m venv .venv
.venv\Scripts\activate          # Windows
source .venv/bin/activate       # macOS / Linux

pip install -r requirements.txt

# 환경변수: .env.example 을 .env 로 복사하고 OPENAI_API_KEY 를 채운다
copy .env.example .env          # macOS: cp .env.example .env

# 문서를 벡터DB에 색인 (문서가 바뀔 때마다)
python -m src.ingest

# 질문 한 번 — 서버 없이
python -m scripts.ask "라벨 품질 이슈가 뭐였죠?"

# API 서버 → http://127.0.0.1:8000/docs
uvicorn src.api:app --reload
```

CLI와 API는 같은 `ask()`를 호출한다. 진입점이 둘이어도 답이 갈릴 수 없다.

검증과 측정은 따로 돌린다.

```bash
python -m scripts.check_tools   # 계산 도구 회귀 테스트. API 호출 없음, 몇 초
python -m scripts.smoke_test    # 설정·DB·LLM·에이전트를 단계별로 확인
python -m eval.run_eval         # 평가 25문항
python -m eval.retrieval_check  # 검색 품질만 따로 측정
```

## 구조

```
src/config.py            설정 한 곳에 모음 (경로·모델·RAG 파라미터)
src/ingest.py            문서 → 청크 → 임베딩 → Chroma
src/tools.py             도구 3개. 이 프로젝트의 핵심 설계
src/agent.py             LangGraph ReAct 루프
src/api.py               FastAPI /ask

scripts/ask.py           CLI 진입점
scripts/check_tools.py   계산 도구 회귀 테스트 (API 불필요)
scripts/smoke_test.py    단계별 동작 확인

eval/run_eval.py         평가 25문항 실행기
eval/retrieval_check.py  검색 품질 측정기
eval/grade.py            수동 채점 반영

data/docs/               RAG 코퍼스 (합성)
data/inspection_results.csv   검사 결과 1,000행 (합성)
```

## 평가

`gpt-4o-mini` · `CHUNK_SIZE=500` · `TOP_K=4` · 2026-10-27 측정
원본: [`eval/results_FINAL_chunk500_topk4.csv`](eval/results_FINAL_chunk500_topk4.csv)

25문항을 다섯 갈래로 나누고, 지표 세 개를 따로 잰다.

| 유형 | 문항 | 기대 동작 | 도구 선택 | 출처 | 사실 근거 |
|---|---|---|---|---|---|
| rag | 8 | 문서 검색 도구 호출 | 100% | 88% | 100% |
| stats | 6 | 통계 도구 호출 | 100% | — | — |
| simulation | 3 | 시뮬레이션 도구 호출 | 100% | — | — |
| refuse | 3 | 도구를 부르지 않고 모른다고 답함 | 100% | — | — |
| leading | 5 | 거짓 전제를 부정하고 사실을 답함 | 100% | 80% | 80% |
| **전체** | **25** | | **100%** | **85%** | **92%** |

- **도구 선택** — 기대한 도구를 실제로 불렀는가
- **출처** — 올바른 문서만 인용했는가. 다른 문서를 같이 인용하면 실패
- **사실 근거** — 정답 대목에만 나오는 문자열이 답변에 있는가

사람이 원문과 대조한 채점은 따로 둔다.

| 항목 | 결과 | 감점 |
|---|---|---|
| 답변 정확도 | 24/25 (96%) | #21 — 답이 코퍼스에 있는데 못 찾고 "언급 없음"이라 답함 |
| 환각 | 0/25 (0%) | 없음 |

### refuse와 leading을 넣은 이유

`refuse` 3문항은 데이터에 없는 것(미래 예측, 외부 정보, 타 도메인 적용)을 물었을 때
도구를 뒤지지 않고 모른다고 답하는지를 본다. 뭐라도 검색해서 근거처럼 붙이기 시작하면
그대로 환각이 된다.

`leading` 5문항은 거짓 전제를 담은 질문이다.
실사용 중 *"F1이 오른 건 재학습이 아니라 평가 데이터 정제인가?"* 같은 질문에 동조하며
근거를 지어내는 것을 발견하고 추가했다. 기존 20문항이 전부 중립적으로 쓰여 있어서
이 유형을 시험하지 못했다.

출처·사실 자동 채점도 처음부터 있던 것이 아니다. 관측된 실패 유형에 맞춰 늘린 것이다.

### 자동 지표를 통과하고도 틀릴 수 있다

`#1`은 내용이 전부 맞는데 출처만 틀렸다. 비용 비대칭도, `conf 0.12`도, `recall 0.977`도
문서와 일치하는데 다른 문서를 출처로 적었다. 도구 선택과 사실 앵커를 모두 통과했으므로
자동 지표로는 잡히지 않는다. 수동 채점 칸을 남겨둔 이유가 이것이다.

`#21`은 반대 방향의 실패다. 답이 코퍼스에 있는데 검색이 엉뚱한 문서를 가져와
"문서에 언급이 없다"고 답했다. 지어내지 않은 것은 옳지만, 못 찾은 것은 오답이다.
거짓 전제의 표현이 검색까지 끌고 간 사례라 [트러블슈팅 8번](docs/TROUBLESHOOTING.md)에 적었다.

### 한계

- **25문항은 유의성을 주장할 표본이 아니다.** 설정을 바꿨을 때 무너지는 지점을 찾는
  회귀 테스트로 쓴다.
- **1회 측정으로는 부족하다.** `temperature=0`인데도 같은 문항의 인용 출처가 실행마다
  달랐다. 엄밀하게는 3회 반복 후 최악값을 보고해야 한다.
- **인덱스와 코퍼스가 어긋나면 지표가 조용히 거짓말한다.** 코퍼스를 고치고 재색인을
  빠뜨린 적이 있는데, 그때 나온 `출처 100%`는 사실이 아니었고 재색인 후 85%로 내려왔다.
  색인이 덧붙기만 하던 버그도 같이 고쳤다.
- **사실 근거 검사는 문자열 포함 여부**라 의미까지 보지 못한다.
  대신 LLM 채점기를 쓰지 않으므로 몇 번 돌려도 같은 값이 나온다.

## RAG 파라미터를 정한 근거

전문은 [`docs/EXPERIMENTS.md`](docs/EXPERIMENTS.md)에 있다.

두 설정을 **컨텍스트 총량을 맞춰서** 비교했다(500×4 ≈ 1000×2 ≈ 1,500자).
총량을 맞추지 않으면 청크가 커서 좋아진 것인지 그냥 더 많이 넣어서 좋아진 것인지
구분할 수 없다.

| 지표 | A (500 / top_k 4) | B (1000 / top_k 2) |
|---|---|---|
| 도구 선택 정확도 | 100% | 100% |
| 검색 정확도 (hit rate) | **100% (8/8)** | 75% (6/8) |
| 평균 컨텍스트 | 1,527자 | 1,490자 |

설정 A를 채택했다. 같은 컨텍스트 예산에 검색 정확도가 높다.

도구 선택 정확도는 양쪽 100%로 포화되어 두 설정을 구분하지 못했다.
그래서 검색 품질 지표를 따로 만들었다.
도구 선택 정확도는 에이전트의 판단을 재는 지표이지 RAG 파라미터를 재는 지표가 아니다.

## 트러블슈팅

전문은 [`docs/TROUBLESHOOTING.md`](docs/TROUBLESHOOTING.md)에 있다.

| 증상 | 진짜 원인 |
|---|---|
| `pip install` 시 `UnicodeDecodeError: cp949` | `requirements.txt`의 한글 주석. pip은 시스템 로케일로 읽는다 |
| `429 insufficient_quota` | 키는 정상, 크레딧 잔액 0. `AuthenticationError`와 구분해야 한다 |
| 답이 문서에 있는데 "모른다"고 거절 | 시스템 프롬프트가 아니라 도구 docstring 문제 |
| 검색은 맞았는데 평가에서 실패 | 평가셋의 정답 라벨이 틀렸다 |
| 계산 결과에 문서 출처를 붙임 | 프롬프트가 아니라 도구 반환값 문제 |

"모른다고 거절"과 "계산 결과에 출처를 붙임", 이 두 건이 가장 값나가는 기록이다.
둘 다 프롬프트를 고쳐서는 아무 변화가 없었고, 도구 쪽을 고쳐야 해결됐다.

| 문제 | 프롬프트 수정 | 실제로 통한 것 |
|---|---|---|
| 답이 있는데 거절 | 변화 없음 | docstring에 코퍼스 주제 열거 → rag 88% → 100% |
| 계산 결과에 출처를 붙임 | 변화 없음 | 도구 반환값 첫 줄에 "계산 결과" 표시 삽입 |

LLM의 행동을 바꾸려면 프롬프트보다 컨텍스트를 바꾸는 편이 안정적이다.
프롬프트는 태도를 정하고, 도구의 명세와 출력은 행동을 정한다.
도구 선택이 틀렸을 때는 **docstring → 도구 경계 → 시스템 프롬프트** 순서로 본다.
이 순서를 모르면 프롬프트만 고치며 시간을 쓴다.

## 알려진 한계

- FastAPI 동기 처리. 요청이 몰리면 대기가 쌓인다. 실서비스라면 작업 큐가 필요하다.
- 인증 없음. 사내망 배치를 가정했다.
- 답변 정확도는 수동 채점이다. LLM 채점기를 쓰면 채점기를 또 평가해야 한다.
- 코퍼스가 문서 4개 규모라 파라미터 결론이 규모에 종속적이다.
- 질문의 어휘와 문서의 어휘가 크게 다르면 검색이 실패한다. 청크 크기로는 해결되지 않고
  하이브리드 검색이나 용어 사전이 필요하다.
