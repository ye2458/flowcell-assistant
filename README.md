# CELLNEX Inspection Assistant

이차전지 셀 결함검사 운영 어시스턴트 — **RAG + Tool-calling Agent**

**CELLNEX는 이차전지 셀 검사 담당자의 세 가지 질문 — 왜 그렇게 판단했나, 몇 건인가,
임계값을 바꾸면 어떻게 되나 — 을 하나의 에이전트가 처리하는 운영 어시스턴트다.**
**문서 검색·표 집계·임계값 재계산을 각각 다른 도구로 분리해, 세거나 계산하는 일은 코드가
하고 LLM은 "어떤 도구를 부를지"만 판단한다.**

> 코퍼스는 비전 검출 프로젝트 **원 프로젝트**(이차전지 셀 미세결함 검출, 8주·팀)에서
> 작성한 평가 프로토콜·실험 이력·라벨 이슈·배포 사양 기록이다.
> CELLNEX는 그 기록을 운영 질의응답으로 잇는 별도 프로젝트다.

검사 담당자가 자연어로 묻는 세 종류의 질문을 하나의 에이전트가 처리한다.

1. **왜 그렇게 판단했나** — 검사 기준·실험 이력·배포 근거 문서 검색 (RAG)
2. **몇 건인가** — 검사 결과 표 집계
3. **바꾸면 어떻게 되나** — 판정 임계값을 바꿨을 때 recall / 재검 부하 재계산

---

## 왜 이 구조인가

### 도구를 세 개로 나눈 이유

`"confidence 0.3 이하인 REJECT 셀이 몇 개인가?"` 를 벡터 검색으로 풀면 반드시 틀린다.
벡터 검색은 *의미가 비슷한 문장*을 찾을 뿐 세거나 더하지 못한다.

- **세는 일**은 결정적이어야 하므로 코드가 한다 → `query_defect_stats`
- **근거를 찾는 일**은 문서에 있으므로 검색이 한다 → `search_inspection_docs`
- **계산해서 판단을 바꾸는 일**은 별도 도구로 분리한다 → `simulate_threshold`

LLM에게 맡기는 것은 **"어떤 도구를 부를지 고르는 판단"** 하나뿐이다.
이것이 RAG 챗봇과 Agent의 차이다.

### `simulate_threshold` 를 넣은 이유

문서 검색만 하는 어시스턴트는 "문서에 뭐라고 쓰여 있는지"를 되풀이할 뿐이다.
이 도구는 임계값을 바꿨을 때의 recall과 재검 부하를 실제로 계산해
**운영 의사결정 자체를 바꾼다.**

원 프로젝트에서 세운 원칙 — *F1 최대점은 배포 운영점이 아니다* — 를
에이전트가 실행 가능한 형태로 옮긴 것이다.

## 실행 순서

```bash
# 0) 가상환경
python -m venv .venv
.venv\Scripts\activate          # Windows
source .venv/bin/activate       # Mac / Linux

# 1) 패키지 설치 → 성공하면 즉시 버전 고정
pip install -r requirements.txt
pip freeze > requirements.lock.txt

# 2) 환경변수
copy .env.example .env          # Windows  (Mac: cp .env.example .env)
#   → .env 를 열어 OPENAI_API_KEY 를 채운다

# 3) 문서를 벡터DB에 인덱싱 (문서가 바뀔 때만 다시)
python -m src.ingest

# 4) 단계별 동작 확인
python -m scripts.smoke_test

# 4b) 계산 도구 회귀 테스트 — API 호출 없음, 몇 초
python -m scripts.check_tools

# 5) 평가 실행 — 도구 선택 정확도
python -m eval.run_eval

# 5b) 검색 품질 측정 — RAG 파라미터를 비교할 때 쓴다
python -m eval.retrieval_check

# 6) 질문 한 번 — 서버 없이 (가장 빠름)
python -m scripts.ask "라벨 품질 이슈가 뭐였죠?"

# 7) API 서버
uvicorn src.api:app --reload
#   → http://127.0.0.1:8000/docs 에서 바로 호출해볼 수 있다
```

CLI와 API는 **같은 `ask()` 함수**를 부른다. 진입점이 둘이어도 답이 갈리지 않는다.

## 구조

```
src/config.py    설정 한 곳에 모음 (경로·모델·RAG 파라미터)
src/ingest.py    문서 → 청크 → 임베딩 → Chroma 저장
src/tools.py     ★ 도구 3개 정의 — 이 프로젝트의 핵심 설계
src/agent.py     LangGraph ReAct 루프 (agent ↔ tools)
src/api.py       FastAPI /ask 엔드포인트
scripts/ask.py          CLI 진입점 — 터미널에서 질문 한 번
scripts/check_tools.py  계산 도구 회귀 테스트 (API 불필요)
eval/run_eval.py        평가 20문항 실행기 — 도구 선택 정확도
eval/retrieval_check.py 검색 품질 측정기 — 정답이 실제로 검색됐는지
data/docs/       RAG 코퍼스 (검사 기준·실험 이력·라벨 이슈·배포 사양)
```

## 평가 결과

`python -m eval.run_eval` · `gpt-4o-mini` · 채택 설정(`CHUNK_SIZE=500`, `TOP_K=4`)
측정일 2026-10-05 · 원본: [`eval/results_FINAL_chunk500_topk4.csv`](eval/results_FINAL_chunk500_topk4.csv)

> ⚠️ **2026-09-29 코퍼스 정정 후 재측정 전.** 아래 결과는 정정 전 코퍼스(`02` · `03`)와
> 정정 전 21 · 23번 문항으로 잰 값이다. 경위와 재측정 순서는
> [`docs/TROUBLESHOOTING.md`](docs/TROUBLESHOOTING.md) 7-e.

25문항을 다섯 갈래로 나눠 측정한다. 지표는 셋이다.

| 유형 | 문항 | 기대 동작 | 도구 선택 | 출처 | 사실 근거 |
|---|---|---|---|---|---|
| rag | 8 | 문서 검색 도구 호출 | 100% | 88% | 100% |
| stats | 6 | 통계 도구 호출 | 100% | — | — |
| simulation | 3 | 시뮬레이션 도구 호출 | 100% | — | — |
| **refuse** | 3 | **도구를 부르지 않고 모른다고 답함** | 100% | — | — |
| **leading** | 5 | **거짓 전제를 부정하고 사실을 답함** | 100% | 80% | 100% |
| **전체** | **25** | | **100%** | **85%** | **100%** |

- **도구 선택** — 기대한 도구를 실제로 불렀는가
- **출처** — 올바른 문서만 인용했는가. *다른 문서를 같이 인용하면 실패*
- **사실 근거** — 정답 대목에만 나오는 문자열이 답변에 있는가

수동 채점(25문항 전수, 사람이 원문과 대조):

| 항목 | 결과 | 감점 내용 |
|---|---|---|
| 답변 정확도 | **24/25 (96%)** | #2 — 무관한 절의 내용을 근거로 끌어붙임 |
| 환각 | **1/25 (4%)** | 같은 문항 — 문서에 없는 인과관계를 만듦 |

### 자동 지표가 전부 통과해도 틀릴 수 있다 ★

**#2 는 도구 선택과 사실 앵커를 통과했지만 내용이 틀렸다.** 올바른 도구를 부르고,
사실 앵커도 포함했는데, **근거로 제시한 내용이 그 질문과 무관한 절에서 왔다.**
문자열 검사로는 원리적으로 잡히지 않는 유형이고, 수동 채점 칸을 남겨둔 이유가 이것이다.

**원문 구조가 검색 품질을 좌우한다.** 2026-09-29 에 코퍼스를 절 단위로 정리하자
같은 유형의 혼동 2건(#3·#7)이 **코드를 한 줄도 고치지 않고** 사라졌다.
RAG 품질 문제를 전부 파라미터나 모델에서 찾으면 안 되는 이유다.

### `leading` 5문항 — 유도 질문

실사용 중 *"0.651→0.798는 재학습이 아니라 평가 데이터 정제인가?"* 처럼 **전제를 담은
질문**에 동조하며 근거를 지어내는 것을 발견해 추가했다. 기존 20문항이 전부 중립적으로
쓰여 있어 이 유형을 시험하지 않았다. 경위는 [`docs/TROUBLESHOOTING.md`](docs/TROUBLESHOOTING.md) 7번.

`refuse` 3문항도 같은 성격이다. 데이터에 없는 것(미래 예측, 외부 정보, 타 도메인 적용)을
물었을 때 도구를 뒤지기 시작하면 그대로 환각으로 이어진다.

**지표는 관측된 실패 유형에 맞춰 늘려야 한다.** 출처·사실 자동 채점과 `leading`
카테고리 모두 처음부터 있던 것이 아니라, 실패를 보고 나서 추가한 것이다.

### 한계 — 먼저 밝힐 것

- **25문항은 유의성을 주장할 표본이 아니다.** 설정을 바꿨을 때 무너지는 지점을 찾는
  **회귀 테스트** 용도다.
- **1회 측정으로는 부족하다.** `temperature=0` 인데도 같은 문항의 인용 출처가 실행마다
  달랐다. 21번은 1차 `01+03` → 2차 `03만`, 7번은 한 실행에서 출처를 아예 누락했다가
  다음 실행에서 정상이었다. 엄밀하게는 3회 반복 후 **최악값**을 보고해야 한다.
- **인덱스와 코퍼스가 어긋나면 지표가 조용히 거짓말한다.** 2026-09-29 에 `data/docs/` 를
  정정했는데 재색인을 하지 않아, 그 뒤의 평가가 **낡은 인덱스**에서 돌았다. 그때 나온
  `출처 100%` 는 사실이 아니었고, 재색인 후 같은 평가가 **85%** 로 내려왔다.
  → 색인 멱등성 버그를 고치고(아래 트러블슈팅) 수치를 다시 측정했다.
- **사실 근거 검사는 문자열 포함 여부**라 의미가 맞는지까지 보지 못한다.
  대신 LLM 채점기를 쓰지 않으므로 몇 번 돌려도 같은 값이 나온다.

## RAG 파라미터를 무엇으로 정했는가

전문: [`docs/EXPERIMENTS.md`](docs/EXPERIMENTS.md)

두 설정을 **컨텍스트 총량을 맞춰서** 비교했다(500×4 ≈ 1000×2 ≈ 1,500자).
총량을 맞추지 않으면 "청크가 커서 좋아진 것"인지 "더 많이 넣어서 좋아진 것"인지 구분할 수 없다.

| 지표 | A (500 / top_k 4) | B (1000 / top_k 2) |
|---|---|---|
| 도구 선택 정확도 | 100% | 100% |
| **검색 정확도(hit rate)** | **100% (8/8)** | 75% (6/8) |
| 평균 컨텍스트 | 1,527자 | 1,490자 |

→ **설정 A 채택.** 같은 컨텍스트 예산에 검색 정확도가 높다.

도구 선택 정확도가 양쪽 100%로 **포화**되어 두 설정을 구분하지 못했고, 그래서
검색 품질 지표(`eval/retrieval_check.py`)를 따로 만들었다.
*도구 선택 정확도는 에이전트의 판단을 재는 지표이고, RAG 파라미터를 재는 지표가 아니다.*

## 트러블슈팅

전문: [`docs/TROUBLESHOOTING.md`](docs/TROUBLESHOOTING.md)

| 증상 | 진짜 원인 |
|---|---|
| `pip install` 시 `UnicodeDecodeError: cp949` | `requirements.txt` 의 한글 주석. pip은 시스템 로케일로 읽는다 |
| `429 insufficient_quota` | 키는 정상, 크레딧 잔액 0. `AuthenticationError` 와 구분해야 한다 |
| **답이 문서에 있는데 "모른다"고 거절** | **시스템 프롬프트가 아니라 도구 docstring 문제** |
| 검색은 맞았는데 평가에서 실패로 나옴 | 평가셋의 **정답 라벨**이 틀렸다 |
| **계산 결과에 문서 출처를 붙임** | **프롬프트가 아니라 도구 반환값 문제** |

가운데 두 건이 이 프로젝트에서 가장 값나가는 기록이다.

**도구 선택이 틀렸을 때 고칠 곳의 순서** — 이걸 몰라서 프롬프트만 계속 고치는 것이
흔한 시간 낭비다.

1. **도구 설명(docstring)** ← LLM이 선택에 쓰는 1차 근거. 여기를 먼저 본다
2. **도구 경계** — 한 도구가 두 가지 일을 하고 있지 않은가
3. **시스템 프롬프트** — 태도와 말투. 선택 문제를 여기서 고치려 하면 실패한다

실제로 두 번 모두 프롬프트 수정은 **아무 변화가 없었다.**

| 문제 | 프롬프트로 고치기 | 실제로 통한 것 |
|---|---|---|
| 답이 있는데 "모른다"고 거절 | 실패 | 도구 **docstring** 에 코퍼스 주제 열거 → rag 88%→100% |
| 계산 결과에 출처를 붙임 | 실패 | 도구 **반환값 첫 줄**에 "계산 결과" 표시 삽입 |

**LLM의 행동을 바꾸려면 프롬프트보다 컨텍스트를 바꾸는 편이 안정적이다.**
프롬프트는 태도를 정하고, 도구의 명세와 출력은 행동을 정한다.

## 알려진 한계

- FastAPI 동기 처리 — 요청이 몰리면 대기가 쌓인다. 실서비스라면 작업 큐가 필요하다.
- 인증 없음 — 사내망 가정.
- 답변 정확도는 수동 채점 — LLM 채점기를 쓰면 채점기를 또 평가해야 한다.
- `data/inspection_results.csv` 는 **문서의 운영점(conf 0.05 → recall 0.977,
  재검 부하 6.6%)을 재현하도록 만든 샘플 데이터**다. 실제 검사 결과로 교체할 것.
  교체 전까지 이 표의 수치를 실제 성능으로 인용하지 말 것.
